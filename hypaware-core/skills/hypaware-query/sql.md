# SQL dialect reference

The query interface is read-only. This reference targets squirreling 0.17.5; older installations or remote deployments may differ.

- **Discover the schema on the selected target.** Use `hyp query schema <table>` (add `--remote <target>` for remote queries) or `SELECT * FROM <table> LIMIT 1`. `SHOW TABLES` lists registered datasets, not columns; `DESCRIBE`, DDL, and `information_schema` are unsupported. Local `hyp cache status` cannot describe a remote.
- **Dataset column names.** On `ai_gateway_messages`, use `conversation_source`, `message_created_at`, and JSON fields under `attributes.usage`, not `source`, `timestamp`/`ts`, or a `usage` column. The otel `logs` and `metrics` datasets do have `timestamp`. On `node`, use `node_type`, `natural_key`, and `label`; on `edge`, use `edge_type`, `src_type`, and `dst_type`. Neither graph table has `type`. Read the real column list in query errors instead of guessing another name.
- **Time filters.** Compare `message_created_at` directly against UTC bounds, e.g. `message_created_at >= '2026-08-18T21:00:00Z'`. Keep the `Z`: zone-less instants use the host's local time. The STRING `date` column filters whole days and prunes partitions (`date >= 'YYYY-MM-DD'`). There is no `DATE()` function; use `date`, `DATE_TRUNC('day', message_created_at)`, or `CAST(message_created_at AS DATE)` (the UTC day). A `DATE 'YYYY-MM-DD'` literal compares as UTC midnight. For month keys, `substr(date, 1, 7)` works too.
- **JSON fields.** Use `JSON_EXTRACT` or `JSON_EXTRACT_STRING(tool_args, '$.command')`; dotted identifiers such as `usage.output_tokens` are not columns. JSON extraction can fail on plain strings that are not valid JSON. Inspect bounded raw examples and narrow to valid JSON records first. Regex over serialized JSON is not a reliable field extractor.
- **Human-typed turns.** A `role = 'user'` text row is not necessarily something a person typed: skill expansions, system reminders, tool-loaded echoes, task notifications, peer-agent messages, interrupts and compaction summaries all land as user text. Since HypAware 1.48.0 (2026-11-02) the row records who submitted it. Claude Code and Claude Desktop: `JSON_EXTRACT_STRING(attributes, '$.claude.origin.kind') = 'human'`; `attributes.claude.prompt_source` adds `typed`, `queued`, `suggestion_accepted`, `sdk` or `system`, and a headless `claude -p` turn carries `prompt_source = 'sdk'` with no `origin`. Codex: `JSON_EXTRACT_STRING(attributes, '$.codex.content_item_kinds') LIKE '%"user.text"%'`; injected blocks carry `agents_md.instructions` or `environments.environment_context` instead. Injected turns carry no label at all, so a NULL means "not typed" only where the label could have been written.
- **Human turns before the label.** Rows written while the capturing daemon ran a version before 1.48.0 never get the label, and the maintenance sweep does not add it later, so a label-only filter undercounts every earlier day and every machine that has not upgraded. Check coverage first: group `SUM(CASE WHEN JSON_EXTRACT_STRING(attributes, '$.claude.origin.kind') IS NOT NULL THEN 1 ELSE 0 END)` against `COUNT(*)` by `date` (or by `gateway_id` on a remote). Where a day has user rows but no labels, fall back to the text heuristic and say in the answer that those counts are estimates. For Claude sources the heuristic is: main thread only (`COALESCE(is_sidechain, false) = false AND (agent_id IS NULL OR agent_id = '')`), `(user_type IS NULL OR user_type IN ('external', 'user'))`, `(entrypoint IS NULL OR entrypoint <> 'sdk-cli')`, and `content_text` not starting with `<`, `[`, `Base directory for this skill`, `Tool loaded.`, `Skill /`, `Re-invocation of `, `Another Claude session sent`, `The user sent a new message while`, `This session is being continued`, `From my HypAware history` or `Message Type:`. It still passes smoke prompts and pasted documents and drops a typed message that opens with a bracket. For Codex before the label there is no reliable text rule: count main-thread `role = 'user'` text rows and state the limitation.
- **Remaining dialect differences.** `LIKE ... ESCAPE`, `datetime`, `strftime`, and `typeof` are unsupported. `regexp_extract(str, pattern, n)` returns capture group `n` (default `0`, the whole match); `REGEXP_SUBSTR` takes a 1-based start position and occurrence and returns the whole match. `UNION` operands need identical column names: alias both sides consistently. Aggregate windows (`COUNT`, `MAX`, `SUM` with `OVER`) are unsupported; aggregate in a subquery instead.
- **Avoid repeated correlated scans.** `EXISTS`, `NOT EXISTS`, `IN` and `NOT IN` subqueries correlated only by equality between qualified columns (`inner.col = outer.col`; a bare inner column such as `col = outer.col` re-scans) read the inner table once, including inside `OR`, in the `SELECT` list, and with computed `IN` values; eligible scalar aggregates can become grouped joins when correlation columns have matching known primitive types. Other forms, including correlated `LIMIT` or `OFFSET`, a non-equality correlation (even next to an equality), or an expression over the outer column in the correlation, may re-scan per outer row. For expensive queries, aggregate in a derived table and JOIN it back, or use `ROW_NUMBER()`.
- **Never retry a memory-budget refusal unchanged.** Narrow the input with a schema-supported time filter and select fewer columns. `LIMIT` or aggregation can shrink results without bounding the scans, sorts, joins, or aggregate state needed to produce them.

Never GROUP BY / DISTINCT / row-fetch wide content columns (`cwd`,
`content_text`) on the messages table at scale. `system_text`, `tools`, and
`attributes` are also expensive: extract needed fields, avoid serializing whole
objects or per-row string transforms. Split expensive reads by date and avoid
concurrent heavy scans.
