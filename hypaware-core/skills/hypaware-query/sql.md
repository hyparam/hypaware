# SQL dialect reference

The query interface is read-only with a deliberately small SQL surface. These examples target squirreling 0.16.13; older installations or remote deployments may differ.

- `SELECT` and `SHOW TABLES` are supported; `DESCRIBE`, DDL, and `information_schema` are not. Discover a table's columns with `hyp query schema <table>` or `SELECT * FROM <table> LIMIT 1`. `SHOW TABLES` lists registered datasets, not their columns. Common datasets are `ai_gateway_messages`, `node`, and `edge`. Inspect other datasets with schema discovery on the selected target; local `hyp cache status` cannot describe a remote. Add `--remote <target>` to schema commands for remote queries.
- Boolean predicates: `IS NOT TRUE` / `IS TRUE` are not parsed (`NOT` must be followed by `NULL`). Compare directly: `col = true`, `col = false`, or `col IS NULL`.
- Cast types are STRING/VARCHAR/TEXT, INT, BIGINT, FLOAT/REAL/DOUBLE, BOOL, and TIMESTAMP; `TRY_CAST` and `TIMESTAMP '...'` literals parse too. On `ai_gateway_messages`, time ranges compare directly against the TIMESTAMP event-time column, `message_created_at` (there is no `timestamp` column): a bare string bound is typed against the column before the query runs, so `message_created_at >= '2026-08-18T21:00:00Z'` selects the rows it names. Keep the trailing `Z`, or a zone-less instant reads as the host's local time. The STRING `date` column still filters whole days (`date >= 'YYYY-MM-DD'`) and prunes partitions.
- `ANY_VALUE` and `REGEXP_LIKE` do exist. `ANY_VALUE` chooses a value from the group; `MAX`/`MIN` choose its extremes and are not equivalent. `REGEXP_MATCHES` is an alias for `REGEXP_LIKE`. `REGEXP_SUBSTR` and plain `LIKE` also work. `LIKE ... ESCAPE` is not parsed.
- `regexp_extract(str, pattern, n)` returns capture group `n`; `0`, the default, is the whole match. `REGEXP_SUBSTR` instead takes a 1-based start position and an occurrence, and always returns the whole match.
- `json_extract_scalar()` does not exist. Use `JSON_EXTRACT` or `JSON_EXTRACT_STRING` (for text), e.g. `JSON_EXTRACT_STRING(tool_args, '$.command')`. Both can fail when a JSON-typed column holds a plain string that is not valid JSON. Inspect bounded raw examples and narrow to records with valid JSON before extracting. A regex over serialized JSON is not a reliable field extractor: escaped quotes, whitespace, and nested objects can change its result. Dotted identifiers (`usage.output_tokens`) are not columns; extract JSON fields explicitly.
- **Column-name traps on `ai_gateway_messages`.** There is no `source` column (it is `conversation_source`), no `timestamp` and no `ts` (the event-time column is `message_created_at`), and no `usage` (token counts live under `attributes.usage`). These are that dataset's traps, not the engine's: the otel `logs` and `metrics` datasets do have a `timestamp` column. A failed query echoes the real column list: read it instead of guessing a second name.
- **Column-name traps on `node` and `edge`.** Neither table has a `type` column. The kind of a node is `node_type` (`Session`, `Skill`, `Repo`, ...), its identity is `natural_key`, its display text is `label`; an edge's kind is `edge_type`, and its endpoints are typed by `src_type` and `dst_type`.
- **More functions that do not exist**, beyond those above: `now`, `datetime`, `strftime`, `group_concat`, `typeof`, `chr`. `STRING_AGG(col, ',')` is the working stand-in for `group_concat`.
- **Date/time functions do exist**, over a `TIMESTAMP` value: `DATE_TRUNC`, `DATE_PART`, `EXTRACT`, `DATEDIFF`, `EPOCH`, and `CURRENT_DATE` all run (`DATE_TRUNC('month', CAST(message_created_at AS TIMESTAMP))`). Grouping by `substr(date, 1, 7)` also works for a month key on the STRING `date` column.
- **There is no DATE type and no `DATE()` function.** Use the `date` column (`MIN(date)`, `COUNT(DISTINCT date)`) or `DATE_TRUNC('day', CAST(message_created_at AS TIMESTAMP))`.
- **`UNION` operands must have identical column *names*, not merely compatible types** ("Set operation operands must have identical columns, got left [t, n] and right [edge, count_all]"). Alias both sides to the same names.
- **An aggregate may appear in `HAVING` or `ORDER BY` without being selected.** `GROUP BY session_id HAVING COUNT(*) > 1` and `ORDER BY COUNT(*) DESC` both run with only `session_id` in the SELECT list.
- **A correlated subquery may re-run once per outer row**, scanning its table again each time. A plain `EXISTS`, `NOT EXISTS`, or `IN` that stands as its own `AND` term in `WHERE` and correlates by column equality (`WHERE EXISTS (SELECT 1 FROM ai_gateway_messages t WHERE t.session_id = m.session_id AND t.role = 'tool')`) can be planned as a semi-join that reads its table once. Eligible scalar aggregates can also become grouped joins when correlation columns have matching known primitive types. Do not assume this optimization applies to every source. Forms such as a correlated subquery with `LIMIT`, `NOT IN`, a test inside an `OR`, or an `IN` over a computed value (`IN (SELECT r.id + 0 ...)`) can still run per row. For expensive repeated scans, prefer aggregating in a derived table and JOINing it back (first message per session: join on `MIN(message_created_at)` grouped by `session_id`), or `ROW_NUMBER()`.
- **`ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` works; `COUNT`, `MAX`, and `SUM` with `OVER` do not.** Aggregate in a subquery, or bucket by time (per minute: `substr(CAST(message_created_at AS VARCHAR), 1, 16)`).
- **Never retry a memory-budget refusal unchanged.** It means execution exceeded its memory allowance, which can include retained results, sorts, joins, or aggregate state. Narrow the input with a time filter supported by the dataset's schema and select fewer columns. A `LIMIT` or aggregate can reduce result size, but does not necessarily bound the work or memory needed before results are returned.
